# XTTS_REMOVAL — pulling XTTS, F5, Voxtral, the language packs and language-learning out of the root

Branch `feat/xtts-removal`, cut from `feat/higgs-engine-option` (1d04a3b6), 2026-09-05.
This is **phase 5** of `docs/E2A_REMOVAL_PLAN.md`, plus **phase 4 branch A** and the
English-only half of open question 2 — both of which Owen ruled on mid-build.

The rulings this implements:

> "remove e2a completely … replace it with narrator" — XTTS "can all be pulled out from
> the root"; Voxtral and XTTS not needed, F5 goes too.
>
> "non-English books will be translated to English; we will never TTS non-English books."
>
> On language learning: "it needs to be rebuilt anyway … clean it all out."

Nothing here touches an e2a **spawn**. Phases 2–3 move prep/worker/assembly to narrator
and are a different branch; every `app.py` / `worker.py` command line this build produces
is byte-identical to `01a3799b` except one deliberate, recorded change (below).

## 1. What was removed

### The XTTS streaming pool (commit 1)

| Deleted | Lines |
|---|---|
| `electron/xtts-worker-pool.ts` | 1,187 |
| `electron/xtts-streaming-bridge.ts` — dead, nothing imported it | 397 |
| `electron/scripts/xtts_stream.py` + its `build:electron` copy step | 653 |

The **streaming contract** — `PlaySettings`, `AudioChunk`, `StreamChunk`, `StreamResult`,
`StreamWorkerConfig`, `DevicePref`, `LoadVoiceOptions`, `EngineState` — moved to
`orpheus-worker-pool.ts`. It lived in the XTTS pool only because XTTS was the FIRST pool;
it was never XTTS's to own. No new `stream-types.ts`: one pool declaring four interfaces
nobody else defines is not indirection worth a module. A second pool is the moment to split.

`streaming-engine.ts` keeps the selector with a one-member union, because that seam is what
makes a voice load OBSERVABLE and what `tts-engine.json`, the TTS Server settings payload
and the browser extension's `config` message are all written against.

`stream-scheduler.ts` lost the "opposite physics" branch — XTTS's solo streamed opener.
Every remaining engine batches, so the predicate could only answer false. The measured Mac
batch-width rates in that header STAY: they are why the ramp exists.

### XTTS voices and "add your own voice" (commit 2)

`xtts-voices.ts`, `components/voice-components.ts`, `components/installed-voices.ts`,
`custom-voices.ts`, the `tts-model` component KIND and every fetch/detect/uninstall branch
for it, the `voices:list-audiobook` IPC, the `custom-voices:*` IPCs, and Settings → Voices.

"Add your own voice" was XTTS end to end — the folder it asked for held an XTTS
`config.json` + `model.pth`, and `CUSTOM_ENGINE` was literally `'xtts'`. **A legacy
`custom-voices.json` on disk is IGNORED, not migrated:** nothing left can load what it
points at, and a migration into a format nothing reads is worse than silence.

### F5, Voxtral, DeepSpeed (commit 2)

`components/f5-env.ts`, `components/voxtral-env.ts`, `components/deepspeed-xtts.ts`, their
`getEnvPathForEngine` rows, their Settings pages and their `env_diagnostics.py` entries.
The ids `f5` / `voxtral` / `xtts` stay in `RetiredTtsEngine`, so a record naming one loads
and displays; `assertRunnableTtsEngine` refuses it by name before any spawn.

### The downloadable language packs and the remote catalog (commit 3)

`components/language-pack-components.ts`, the `language-pack` KIND, Settings → Languages,
`LanguagePackService`, the first-run step — and with them `components/catalog-service.ts`
and `components/catalog.bundled.ts`, which served exactly two lists (the XTTS voices and the
Stanza languages) and had nothing left to answer. `catalog.bundled.ts` is generated by
`tools/catalog-indexer/`; it was **deleted, not hand-edited**.

### The language-learning / bilingual feature (commit 4)

`bilingual-assembly-bridge.ts`, `language-learning-jobs.ts`, `queue-steps/bilingual.ts` and
its three registrations, ~700 lines of LL/bilingual/sentence-cache IPC in `main.ts` and
their preload blocks, `src/app/features/language-learning/**` (bilingual player, alignment
window and route, completed-list, URL input, language selector, EPUB resolver), twenty
`languageLearning*` methods on `ElectronService`, the listen window's bilingual arm, and the
`--bilingual` / `--bilingual_pause` / `--bilingual_gap` tail of the assembly argv.

Two files were **split** rather than deleted:

| Was | Is | Why |
|---|---|---|
| `bilingual-processor.ts` (1,712 lines) | `text-ai.ts` (~450) | `callAI` + its four providers, `LANGUAGE_NAMES`, and the Intl.Segmenter splitting behind `splitForTts` — read by tts-api-server, reader-stream-bridge and book-render-service. `BilingualProcessingConfig` → `AiCallConfig`. |
| `ll-jobs.ts` (2,125 lines) | `mono-translation-job.ts` (~940) | `runMonoTranslation` is the LEDGER'S translate pass (`processing-passes.ts`), a different feature. `runLLCleanup` / `runLLTranslation` were the bilingual pipeline's and went. |

Two components moved out of the doomed directory first, because neither was ever
language-learning's: `ArticlePreviewComponent` → `studio/components/article-preview/`, and
the TTS engine registry → `core/models/tts-engine-registry.ts`.

### Sampling settings

`ttsTemperature` / `ttsTopP` / `ttsRepetitionPenalty` (and `topK`) left `PipelineDefaults`,
`PipelinePreset`, the narration modal, `NarrationRunSettings`, the queue config and
`ParallelTtsSettings`. **Measured before deleting**, because the instruction was to check:
the only code that read them was the prep spawn's `if (settings.ttsEngine === 'xtts')` flag
block, and Orpheus and Higgs both declare `sampling: {}`.

One real fallback died with them: `correct-sentences-bridge.computeTakeTemperatures` based
its re-roll spread on `settings.temperature ?? 0.6`. On every Orpheus book the base WAS 0.6,
arrived at through the fallback rather than stated. It is a named constant now.

## 2. What STAYS, and why

| Kept | Reason |
|---|---|
| `'xtts'` / `'f5'` / `'voxtral'` in `RetiredTtsEngine`, and every `'xtts' \| 'orpheus'` **record** DTO | A job written last year says `xtts`. It must load and display. Narrowing those types is what would stop it. |
| `manifest-migration.ts:480,711` (`engine: 'xtts'`) | A statement about history, and a true one. |
| `components/cuda-tts.ts` | **The one deviation from the inventory's delete list, and it is measured.** It is a CUDA PyTorch overlay for the BUNDLED env, and two other things read that torch: faster-whisper transcription (`whisper-env.ts` says so in its own header) and `resolveTtsDeviceArg`'s `auto` resolution, which answers CUDA when the pack is installed. Deleting it would have silently made transcription CPU-only and resolved native-Windows Orpheus jobs to CPU. Its header now says what it actually is; the component **id** stays `cuda-tts` because installed records are keyed on it. |
| `stanza-en.tar.gz` in `RUNTIME_ASSETS` + `ensureEnglishStanza` | **The second deviation, also measured.** e2a's prep still builds a Stanza pipeline for English — `lib/core.py` does `stanza.Pipeline(..., dir=$STANZA_RESOURCES_DIR)` for every language in `year_to_decades_languages` and `return []`s the whole chapter list if it raises. Dropping the download breaks every render on a packaged install TODAY. Phase 6 retires it with the e2a runtime. |
| `ttsSpeed` and `enableTextSplitting` | The worker argv passes `--speed` and `--enable_text_splitting` **ungated by engine**. That is Phase 3's spawn code. |
| `TtsJobConfig` / `tts-bridge.ts`'s four sampling fields | `tts-bridge.ts` is the legacy single-process e2a door and passes `--temperature/--top_p/--top_k/--repetition_penalty` unconditionally. e2a spawn code; Phase 2/3 owns it. |
| `--tts_engine xtts` in `parallel-tts-bridge.ts:asmEngineArg` and `reassembly-bridge.ts` | Engine-agnostic scaffolding — assembly combines audio and never consults the name. Phase 3 drops the literal. |
| `language-learning:fetch-url` / `:finalize-content` and the library's `language-learning/projects/` layout | The studio's "add from a URL" door and the writer of the article EPUB — neither is about bilingual books, and the on-disk layout is where every existing article lives. The channel names are the wire contract with preload and `ElectronService`. |
| `outputs.bilingualAudiobooks`, and `pipeline.bilingualAssembly` as an untyped key | A project with either still OPENS and round-trips through a save — pinned by `tools/test-legacy-bilingual-manifest.js`. A legacy `bilingual:<pair>` variant is skipped by the listen window rather than handed to a player that no longer exists. |
| `shared/queue/engine-types.ts`'s `bilingual-*` job types + their display labels | A legacy queue row still DISPLAYS. The engine refuses to SCHEDULE it by name, because its step module is no longer registered. |
| `tools/catalog-indexer/` and `components/catalog-types.ts` | The indexer also writes the `manifest.json` the UPDATE system reads; the two interfaces are still the shape of its `voices`/`languages` fields on the wire. Retiring those fields is packaging's call. |

## 3. The one deliberate argv change

`tools/snapshots/orpheus-argv-base.json`'s **assembly** row lost its last tokens:

```
...(config.bilingual?.enabled
  ? ['--bilingual', '--bilingual_pause', …, '--bilingual_gap', …]
  : [])
```

The only writer of `config.bilingual` was the language-learning wizard, so an ORPHEUS
assembly took the `: []` arm on every run, before and after. This is a change to the argv's
TEXT, not to any Orpheus job's argv. The keeper's header records it as its one licensed
regeneration; **every other row is still byte-for-byte `01a3799b`**, including `prep` —
the XTTS sampling block deleted there was `args.push` AFTER the array literal the snapshot
captures, and it was gated on `ttsEngine === 'xtts'`.

## 6. What the review round closed

Six things the compiler could not see, found in review and fixed on this branch:

- **`electron/sentence-alignment-window.ts` was fully orphaned but still wired at
  startup.** Its one caller was the bilingual translate pipeline;
  `validateAndAlignSentences` had none left, but `main.ts` still called
  `setupAlignmentIpc()` (four handlers nothing invoked), preload still exposed an
  `alignment` API nothing in `src/` called, and the module still `loadURL`'d
  `#/alignment` — a route this branch had already deleted from `app.routes.ts` while
  leaving it in `window-role.ts`'s `STANDALONE_ROUTES`. Module, import, setup call,
  preload block and route constant all gone.
- **The three `bilingual-*` job types are in `RETIRED_JOB_TYPES`** now, with the same
  actionable sentence the other nine carry. They were safe before — the engine refuses a
  type no module claims — but they hit the generic "nothing in this build knows how to run
  it" instead of saying what happened and what to do instead.
- **The `tts-model` component KIND is gone**, along with its `installTarget:
  'e2a-hf-cache'` and `hf` download coordinates, the renderer's mirror of all three, the
  Add-ons filter for a kind that cannot occur, and the vacuous `tts-model` /
  `language-pack` rows in `test-component-upgrades.js`.
- **`RetiredTtsEngine`'s doc block said two false things** — that XTTS's e2a path was "NOT
  deleted … bilingual books still render through it", and that f5/voxtral's env wiring was
  "untouched". Rewritten.
- **`docs/TTS_API.md` described the server as fronting "a pool of XTTS worker processes
  (default 4 on CPU)".** Rewritten for the one-process batching Orpheus engine, including
  the field an extension author actually acts on: `deviceWorkers` is now the batch width
  to keep in flight, not a process count.
- **`cancelStreaming` had no caller** once the scheduler's streamed-opener branch went, so
  it is off the `StreamingEngine` interface and out of the pool. Orpheus generation is not
  interruptible mid-sentence anyway; the scheduler drops stale results and
  `cancelPendingBatchIfStale` is what abandons a doomed batch.

And one pre-existing bug on `main`, fixed here because this branch had already solved its
twin: **`getPipelineDefaults` spread a stored `ttsEngine: 'xtts'` straight over the
defaults.** The engine button group then showed nothing selected and every run threw at
`assertRunnableTtsEngine`, from the one page that could have repaired it. It now mirrors
`getSelectedEngineName` exactly, through a shared rule (`resolveSavedTtsEngine` in
`engine-caps.ts`) so main and the renderer cannot drift: a retired id migrates to Orpheus
with a `console.error` naming it and the settings rewritten, an unknown id throws by name,
and the VOICE resets with the engine — an Orpheus engine beside a Scarlett clip is the
unrenderable pair the repair exists to prevent. Pinned by
`tools/test-retired-engine-settings.js`.

## 7. Loose ends this branch did NOT close

Honest list, none of them load-bearing:

- **`splitForTts`'s 240-char default is still XTTS's number.** Both streaming callers now
  always pass `orpheusStreamMaxChars(voice)`; `book-render-service` cannot, because it builds
  its sentence plan before a voice is chosen. For it the number is a conservative floor, not a
  correct one. Fixing it means moving the split to render time — a change to that service.
  Flagged in `text-ai.ts` where the constant lives.
- **`audiobook-player`'s Bilingual/Traditional version toggle** is dead UI: it only appears
  when a book carries `bilingualAudioPath` + `bilingualVttPath`, and nothing sets those any
  more. Left in place rather than unpicked from a 900-line player.
- **`video-assembly-bridge.ts`'s `mode: 'bilingual'` arm** has no producer left. The mono arm
  is live; the union keeps the value for legacy queue rows.
- **`studio.types.ts`'s `bilingualOutputs` / `bilingualAudioPath` fields** and
  `MainTab: 'bilingual'` survive as legacy shape.
- Every remaining mention of "xtts" across `electron/ src/ shared/ cli/` is a comment, a
  retired-id declaration, a record DTO, the migration, or the engine-agnostic
  `--tts_engine xtts` assembly literal — no live XTTS code path.
