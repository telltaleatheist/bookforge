aren't completely worked out. Let's go on another full bug hunt."*

where a runtime consequence could not be confirmed it says "verify".

Severity: **HIGH** = a run breaks or work is lost. **MED** = real but recoverable,
or GPU time wasted. **LOW** = wording, drift, seconds. **DESIGN** = a decision

## A. The Foundry job lifecycle (F-findings)

Hunter: BookForge's `foundry-job` step → the vendored Foundry host
(`foundry-app/electron/{job-queue,book,workspace,ipc,crucible-dispatch}.ts`) →
the Foundry CLI (`/Volumes/Callisto/Projects/foundry/src/clean/*`, `translate/*`).
CLI anchors are relative to that repo.

### F1 · HIGH · Retry and resume replay a scratch path the settle already deleted (S9)

`workspace.ts:1738` `planCleanup` → `:1793` `bookPath: derived.path`, minted by
`book.ts:1549` as `derived/<uuid>.book.jsonl` AT PLAN TIME. The whole request
crosses the seam (`job-queue.ts:2068` `host.enqueue`) and is persisted on the
BookForge step (`electron/foundry-host-queue.ts:253` `FoundryJobRequest`).
`job-queue.ts:2862` `sweepDerivedBook` unlinks `request.bookPath` at EVERY
settle — success, failure and cancel alike (`:5481`, `:2736`, `:1242`, `:4119`).
`electron/queue-engine.ts:2240` `retry()` resets status/error/progress/output and
never `step.config`; `queue-steps/foundry-job.ts:463` re-sends
`config.request` byte-identical; `materializeDeferred` (`job-queue.ts:703`)
returns a press-time plan untouched. Result: `--book … cannot be read (ENOENT)`.

**Root cause.** Every OTHER spawn-time artifact is minted at spawn inside
`executeJob` — the `seedRecords` copy (`:5163`), the analysis checklist
(`:5212`) — so a row that never commits leaves nothing. `bookPath` alone is
minted at plan, and its lifetime (plan → settle) is shorter than the row's
(plan → terminal → across restarts). Second deletion path: `book.ts:1440`
`sweepStaleDerived` removes any derived book older than 24 h on the next
materialise in that project — a never-settled row rots after a day.

**Siblings.** `planExport` (`workspace.ts:1454`), `planAnalysis` (`:1867`),
`planTranslation` (`:1674`), `planSimplification` — all four carry the same
`bookPath` and the identical defect. The narrowed export stamp
(`job-queue.ts:2900`) goes with it. Not affected: the cleanup's `--stamp`,
`recordsPath`, `readingsPath`, the checklist, `seedRecords` (F8).

**Fix shape.** Materialise the book AT SPAWN, inside `executeJob`, for every
request carrying a `bookPath` — make `bookOf(request)` a maker, owned by
`job-queue.ts` beside the seed copy and the checklist. (Alternative keeping
plan-time: `bookOf` re-materialises when the file is gone — still one module.)

### F2 · HIGH · A failed clean pass writes NONE of the answers it paid for (S6)

`src/clean/run.ts:659` awaits `askAboutEach(...)` to completion; the
`appendRecord` loops (`:751`, `:771`) run AFTER it. The log line at `:559-561`
— *"every block is asked of the model and recorded there as it lands"* — is
translate's sentence (`records.ts:394`) copied without translate's mechanism:
translate appends inside its `accept` callback (`src/translate/run.ts:2401`,
`:2488`); `askAboutEach` (`tts-number-normalizer.ts:2011`) writes into a local
`answered` map until the pool drains (`:2126-2131`: *"the pass is over either
way and nothing is written"*). `records.append` (`records.ts:300-309`) IS
per-row fsync'd — the durability exists and clean does not use it. 351 of 940
answers, ~45 min of GPU, garbage-collected. The queue's whole resume story
rests on the docblock at `job-queue.ts:3303` (*"interrupted at block 900 of
2,000 resumes for the price of the remaining 1,100"*), which the code does not
deliver. **Twin confirmed:** `src/clean/epub.ts:565` awaits, then `:613`
`bank.append` inside a loop whose own comment (`:611`) claims *"banked the moment
the block has settled"*.

**Fix shape.** `askAboutEach` takes an `onSettled(key, outcome)` sink fired the
moment a verdict is validated; `appendRecord`/`bank.append` move onto it. Safe:
one row per position per run, `rowFor(parts)` reads the newest, so file order
is irrelevant to readers. `tts-number-normalizer.ts` owns it; both callers share
the loop.

### F3a · HIGH · 12 in flight, chosen by nobody, against a serial backend with a TOTAL deadline (S6)

`src/translate/model-server.ts:182` `DEFAULT_TEXT_CONCURRENCY = 12`;
`run.ts:680` takes it when the request states none; `foundry-app/shared/types.ts:1091`
declares `concurrency?` and NOTHING sets it (BookForge deliberately sends none,
`queue-steps/foundry-job.ts:305-309`; Foundry never sets it). Every Crucible
placement is `door: 'openai'` (`crucible-dispatch.ts:1122`). The default's own
docblock states the assumption that makes it safe — *"the server admits what
fits in its KV cache and QUEUES the rest"* — false against a Crucible chat proxy
fronting a serial `mlx_lm`. And `transport.ts:139` `REQUEST_TIMEOUT_MS =
300_000` is armed at SEND (`:170-171`): a total deadline, not inactivity, so the
12th request's clock covers the 11 ahead. Any per-block time above ~27 s times
out the tail. The observed failure is the queueing, not the model.

**Fix shape.** Concurrency is a property of the PLACED server, and
`crucible-dispatch.ts` is the only module that knows which answered: state it on
the `Placement` (from the capability row, as it already does for
`PAGE_READER_CONCURRENCY`) and let `doorArgs` emit `--concurrency`. Absent a
stated number, pool depth and deadline must at least agree
(`timeout ≥ concurrency × worst-block`).

### F3b · HIGH · The engine's own timeout is not recognised as a transport failure, so there is NO re-roll

`transport.ts:178-180` replaces an `AbortError` with `"<url> — no answer in
300s"`; `tts-number-normalizer.ts:1829-1831` `isTransportFailure` regexes
`/fetch|network|ECONNREFUSED|ECONNRESET|socket|timeout|EHOSTUNREACH|ENOTFOUND/i`;
`"no answer in 300s"` matches none. A dropped socket (`fetch failed`) re-rolls;
the engine's own deadline throws on attempt 1 (`:1857`) — and by F2 that
discards the run. Two modules spell one fact: transport composes prose and
throws away the cause; the normaliser regexes the prose back.

**Fix shape.** `TransportError` (`transport.ts:72`, already a class) carries
`cause: 'timeout' | 'network'`; `isTransportFailure` reads the field.
`transport.ts` owns it. Related, unverified live: `vllm.ts:137` `BUSY_STATUSES =
[429]` — a Crucible `503`/`409` on the chat door is a hard failure of the book,
never a wait (`withBusyWait`, `transport.ts:281`, never sees it).

### F6 · HIGH · Retry-one-step revives a row but leaves its narration cancelled

`queue-engine.ts:1659-1673` `cascadeCancel` is TRANSITIVE (whole subtree);
`:2256-2260` `retry({stepId})` resets ONE level (`parentStepId === found.step.id`).

**Fix shape.** `retry({stepId})` resets the same transitive subtree
`cascadeCancel` cancelled, skipping `done`. `queue-engine.ts` owns both walks.

### F7 · MED · The engine's stdout/stderr lands nowhere on disk, and Retry erases the one persisted copy

`foundry-app/electron/engine.ts:172-186` accumulates stdout/stderr in memory
strings; `job-queue.ts:5406`, `:6023`, `:6038` use bare `console.*`; nothing

only — `step.error` (full stderr, persisted). `retry()` (`queue-engine.ts:2243`)
and the resumable-stop branch (`:4287`) set `step.error = undefined` — which is
why tonight's ENOENT left nothing: the retry overwrote the clean failure's
account.

**Fix shape.** `mount.ts` hands the host a line sink so `runEngine`'s `onLine`
tees into a `RollingLogger('foundry-engine')`; `retry()` moves `step.error` to
`lastError` instead of deleting it.

Hunter: `electron/queue-engine.ts` pump/settle/retry/revive/persist,

### Q1 · HIGH · `releaseVenueIfNothingStands` is dead for every narration run — A1 is back, through the `prepare` row

`queue-engine.ts:2223-2229`: `if (job.steps.some(s => s.status === 'done' ||
s.status === 'running')) return;`. `prepare` (CPU, local, no venue) heads every
run composed since Sep 19 and lands `done` first. So when `tts-conversion` takes
server A, A answers `409 server_busy` (a stranger holds it), and the busy branch
(`:4097-4225`) calls `releaseVenueIfNothingStands`, the guard trips on the
completed LOCAL step and the venue stands. `decideWaitFor` takes rung 1 forever;
the book waits hours on the busy machine beside an idle one; its picker is
read-only. A1 verbatim, reached through the row the A1/A2 fix itself added.

**Root cause.** The predicate asks whether ANY step stands; the rule is "nothing
of this run stands ON THAT MACHINE". A local CPU step stands on no machine.

**Fix shape.** Test only TRAVELLING steps (`s.travels === true && (done ||
running)`); `isTravellingGpuStep` (`slot-sets.ts:536`) already spells it. Keeper
gap: `tools/test-queue-admission.js:583-621` drives a ONE-step job; add the
prepare→tts shape.

### Q2 · HIGH · `retry(stepId)` resets DIRECT children only; a cascade-cancelled grandchild stays cancelled (= F6)

`queue-engine.ts:2256-2260` walks one link; `cascadeCancel` (`:1659-1681`) and
`removeStep` (`descendantsOf`, `:1410-1424`) are transitive. Chain prepare → tts →

resets tts and align only; reassembly stays `cancelled`; the render and align
re-run (hours) and then the job is terminal with no m4b and no sentence.
**Fix shape.** `retry` uses `descendantsOf`, mirror of `cascadeCancel`.

### Q3 · HIGH · The whole non-409 refusal class FAILS (= C1, with the table)

`crucible/job.ts:259-265` (no `busyLine` on `CrucibleUnreachable`),

### Q4 · MED · A hosted Foundry act refused `409 leased` by Crucible reddens the row

`queue-steps/foundry-job.ts:585-591` mints a bare `Error` from `row.error`; no
`busyLine` anywhere in `foundry-job.ts` or `foundry-host-queue.ts`. The vendored
window's `crucible-dispatch.ts` takes the lease itself, so a `409 leased`/`server_busy`
arrives as a Foundry row in state `failed` carrying prose. A5 was fixed for the

**Fix shape.** `FoundryJobRow` carries an optional `busyLine` from the mount
(Foundry already distinguishes `standing` waits); `foundry-job.ts` uses
`stepFailure(row.error, row.busyLine)`. Needs the Foundry side's agreement on the
wire field.

### Q5 · HIGH · The startup scratch sweep deletes what a live step's PARENT produced

`main.ts:3057-3085` `liveStepIds` composes `wantedByQueue` from step ids and
implied-export basenames read off `step.config.*` / `step.sourceRef.path`; it
never reads `step.output`. Two kinds fall through:

1. **The prepared session.** `prepare` writes `<scratch>/ebook-<uuid>/` (uuid =
   `crypto.randomUUID()`, `parallel-tts-bridge.ts:3630`); its location lives
   only in `prepare.output.sessionDir`. After a restart with `prepare` done and
   `tts-conversion` held — **exactly the state of Hitler's People and Pursuit of
   Power right now** — the sweep classifies it as a leftover, rescues it (no
   audio) and REMOVES it. Start then refuses by name (`:7540-7551`, "queue the
   book again"), and neither `retry({stepId})` nor `retry({jobId})` re-runs the
   `done` prepare. Only Remove + re-queue recovers.
2. **`<scratch>/narration-cuts/`** (the narration cut cache, `:7132`) is a
   top-level scratch kind nobody names in a live step, so it is `rm -rf`'d on
   every start by the module's own "anything else at the top level" rule.
   `prepared.epubPath` points into it.

**Root cause.** `wantedByQueue` models "what a step names in its CONFIG"; the
prepare→render seam moved the fact into an OUTPUT. The scratch-sweep contract
says a scratch kind that must survive says so by being named in a live step —
two new kinds do not.

**Fix shape.** `liveStepIds` also walks `step.output`
(`sessionDir`/`processDir`/`path`) on every non-terminal step AND on the done
parent of a non-terminal step; `narration-cuts` becomes a named survivor (it is
a content-addressed cache — arguably it belongs outside the swept root).

### Q6 · HIGH · A mid-chain reserve refused for a REASON parks forever WHILE HOLDING THE CARD

`queue-engine.ts:3208-3217` (`settleReserve`'s non-busy arm): `reserveHolds.set(...)`,
`holdStep(step, "Waiting for <server>: <reason>")`, status stays `queued`. A
book's render is `done` on A (the run holds A's card); the next act's reserve is
refused for a non-holder reason (`model_not_resident`, a capability never probed,
`crucible_unreachable` on the reserve). `gpuHoldOf`: started + a `queued` next
act → hold stands; A's only slot is charged; the row re-reserves every 15 s
forever; every other book bound for A reads "holding the card for <title>" with
no clock; nobody is told to intervene. A FAILED step would give the card back;
this park deliberately does not fail.

**Fix shape.** A ceiling. Preferably `settleReserve`'s non-busy arm escalates to
`failed` after N consecutive refusals with the same message (ruling 3: fail
only on a misconfiguration somebody can repair — this is one); the count rides
on `reserveHolds`. `queue-engine.ts` owns it.

### Q7 · MED · A dropped event stream leaves the Crucible job alive and the queue believing the card is free

`crucible/job.ts:598-607`, `render-artifacts.ts:251-258`: the ledger row is

inferred.)

### Q8 · MED · A held mid-chain step files the run under "waiting", and the bench offers a Start that does nothing

`engine-types.ts:945-950` `jobStatus`: live = [held tts, waiting align, waiting
reassembly] → `waiting` (a run that needs a human press filed as waiting on a
parent). `bench.ts:1037`, `:1123` `startable: step.status === 'held'` with no

suppressed on exactly the run that needs it.
**Fix shape.** `startable` = held AND (parent done or SOURCE_PARENT); `jobStatus`
ranks `held` above `waiting` when any live step is held. Both pure, keeper-drivable.

## H. Foundry as a runner — the design (ruling 1, PK6)

### What exists today, read straight

The seam is already half a runner. A press in the hosted window →
`foundry-app/electron/job-queue.ts` `enqueueTextPass` → `planCleanup`/`planTranslation`/…
(`workspace.ts`) → `hostQueue().enqueue(request, parentStep)` → BookForge's
`foundryHostQueue.enqueue` (`electron/foundry-host-queue.ts`) composes a queue
job whose `foundry-job` step carries the WHOLE `EngineRequest` as
`config.request`. BookForge's engine admits it (poll → reserve → slot, the hold),
`queue-steps/foundry-job.ts` calls `foundryRunner()(config.request, {parentStep,
signal, waitFor, onProgress})` → Foundry's `runJob` → `runDetached` → `placeRun`
(→ `crucible-dispatch.placeJob`: which server, the model lease) → `executeJob`
(args, `runEngine`) → settle (`sweepDerivedBook`) → a `Job` row whose `state`
BookForge reads as a string. When hosted, Foundry's own `start/release/cancel/remove`
forward to the host; its `jobs[]` exists only to draw rows the host pushes back
(`setHostQueueRows`).

So Foundry does NOT run a second scheduler when hosted. What it still owns, and
should not, is five things that belong to the ONE lifecycle:

| Owned by Foundry today | Why it breaks | Goes to |
|---|---|---|
| The PLAN, made at press time (`bookPath`, `seedRecords`, `generation`) and persisted verbatim on BookForge's step | scratch outlives its owner's settle; Retry replays a dead path (F1, F5, F8) | materialise AT SPAWN inside the runner |
| The outcome as a `state` string + prose `error` | a busy card cannot park; the failure text is one overwrite from gone (Q4, F7, P5, P6) | a typed outcome |
| A 30 s internal spin on a placement wait (`placeRun`'s `for(;;)`) | the engine already knows how to park; a spin inside the runner is a second scheduler | return `wait` immediately with the holder's line |
| The concurrency the CLI is told (nothing — so the CLI's 12) | a serial engine behind a proxy starves the tail (F3a) | the placement states it |
| Its stdout/stderr, in memory | nothing on disk (P5) | a line sink the host tees |

### The rule

**BookForge's queue is the lifecycle. Foundry, when hosted, is a runner: given a
DESCRIPTION of one act and a VENUE, it plans, places, spawns, and returns a
typed OUTCOME. It stores nothing across calls and decides nothing about when.**

### The wire, both directions

**1. What crosses at press time (identity only).** `FoundryJobRequest` keeps
`kind`, `inputPath`, `to`, `rewrite`, options, `after`/`forStep`, and the
ledger IDENTITY the ghost row needs — `stepId` and `recordsPath` from
`recordsForTextPass` (cheap: a `mkdir readings/` and a name; no model work) —
plus `at: string | null` (the ledger step to make it from) or `deferral: { from }`.
It does NOT carry `bookPath`, `seedRecords`, `generation`, or any path under
`derived/`. `workspace.ts`'s `plan*` split into `identify*` (press) and
`materialize*` (spawn); `enqueueTextPass` calls only the first. The ghost-row
machinery (`promisedStepsIn`, `aimedAt`, `pendingRowAt`, `deferralFor`) is
untouched — it needs the promised `stepId`, which is still minted at press.

**2. What the runner is handed at spawn.**
```ts
runJob(request, {
  parentStep, signal,
  venue: { server: string } | null,   // the card the BookForge job holds/was admitted to; never re-decided
  onLine: (line: string) => void,      // EVERY stderr line — the host tees it to the foundry log
  onProgress: (line: string) => void,  // the row's message, as today
  onPlaced: (p: { server: string; model: string; leaseId: string | null; concurrency: number }) => void,
})
```
`onPlaced` fires once, before the CLI spawns; BookForge writes it into the
in-flight ledger (P8's hosted-lease gap closes here) and settles it when the
outcome arrives.

**3. What comes back.**
```ts
type RunOutcome =
  | { outcome: 'done'; row: FoundryJobRow }
  | { outcome: 'failed'; row: FoundryJobRow; error: string; stderrTail: string }
  | { outcome: 'wait'; busyLine: string; standing: boolean }   // Contract 2, typed
  | { outcome: 'cancelled'; row: FoundryJobRow };
```
`wait` is returned the moment `placeJob` answers `wait` — no internal spin. A
`standing` wait (a server switched off, no engine available) is still a wait:
BookForge parks and the reach sweep re-asks. `foundry-job.ts` maps `wait` →
`stepFailure(busyLine, busyLine)` (parks), `failed` → `stepFailure(error)` with
`stderrTail` written to the foundry log and to `step.lastError`.

**4. Materialise at spawn, in `executeJob`, beside the seed copy and the
checklist.** `bookOf(request)` becomes a MAKER: resolve `at`/`deferral.from` →
ledger step (or fail by name: "the step this was to be made from never
landed"), `materializeBook(dir, step)` → `derived/<uuid>.book.jsonl`, resolve
`seedRecords` = `newestCleanRecords` NOW (and log by name if a seed was expected
and is gone — F8), `generation` NOW. `sweepDerivedBook` at settle stays exactly
as it is — the file's lifetime is now spawn → settle, which is the row's own
run. `materializeDeferred` disappears into this (a deferral is just an `at`
that did not exist at press).

**5. Venue and lease.** The runner places on the venue it was handed — never
`ANY_SLOT` re-decision when hosted (BookForge's engine already chose, and under
ruling 9 holds that card for the whole book). The MODEL lease stays Foundry's
and stays per act: it protects residency between chats, and the next act of the
book may need the card for a voice, not the model. A `409 leased`/`server_busy`
from the venue's own Crucible → `wait` → BookForge parks; under ruling 9 that is
`parkOnOwnTail` (2 s re-ask), so a stranger's chat that took the lane between
acts costs seconds, not a red row.

**6. Concurrency.** `crucible-dispatch.placeJob` puts `concurrency` on the
`Placement` from the placed server's capability row (as it does for the page
reader); absent a stated number, 4 on a Crucible chat door (ruling 4).
`doorArgs` always emits `--concurrency`.

**7. `stopFoundry()`** returns `queue.drained()` — the settle promise — so the
quit chain's 45 s budget is real (P9).

### What this removes

`materializeDeferred`; the plan-time `bookPath`/`seedRecords`/`generation` on
every request type; `placeRun`'s wait loop and its 30 s cap; the
`hostedCrucibleServerNotOffered` pre-check in `foundry-job.ts` (a `standing` wait
says the same thing, typed); the string-parsing of `row.error` for a wait; the
docstring at `job-queue.ts:3303` that promises a resume the code did not do
(after F2 it does).

### What this keeps

Foundry standalone (not hosted) is unchanged: its own `enqueueHere`/pump keeps
planning at press because there is no host and no retry-from-elsewhere; the
identity/materialise split is used by both paths, so standalone gets spawn-time
materialisation for free. The ghost rows. The lease. `sweepDerivedBook`. The
CLI's flags. IPC channels (`IPC-CHANNELS.md`) — nothing the renderer sees changes.

  runs under a 60 s watchdog: a row that has not settled is a **FAIL naming the
  scenario**, never a hang, because a keeper that hangs reads as "still running"
  until somebody gives up on it. The stream-breaking rows now assert the
  LADDER'S OWN LINES: S5a zero rungs (the SDK's `events()` resumes a single
  stale keep-alive socket itself), S5 every rung, `restart` exactly one and then
  the server's `unknown_job`. **19 scenarios, 19 pass, 0 pending.**

- **ONE EXIT, NOT TWO — a stall used to leave its own ledger row standing
  (MED).** Both doors settled the ledger from inside the stream loop (on the
  terminal frame) and swept the server from inside the `catch`. That is two
  reconcilers for one question, and the stall fell straight between them: the
  stall clock cancels the job BY NAME and then throws, so there is no terminal
  frame and the `CrucibleStreamWentQuiet` arm threw before the sweep — leaving
  `crucible-in-flight.json` naming a job this app had itself DELETEd for the
  rest of the session. Every ending of a stream now reconciles at ONE exit
  through `reconcileStreamEnding` (`in-flight-sweep.ts`), which is the only
  place that decides what an ending costs: `terminal` / `cancelled` / `gone`
  **settle** the row (each is a verified state — the server said the job ended,
  answered our DELETE, or said it has no such job), `artifacts-owed` **keeps**
  it, and only `lost` **sweeps**. No second DELETE on a stall: a client that
  cancels a job twice is arguing with itself. `cancelAnswered` is the receipt
  that tells them apart — a cancel that never got through reads `lost`, and the
  sweep is then exactly right.

- **ONE 500 ON ONE ARTIFACT NO LONGER DISCARDS A JOB THAT RAN (MED/HIGH).**
  `writeArtifactsTo` begins each download as its frame lands and raises the
  first failure at the next yield boundary — often before the `done` frame has
  been yielded — so a single failed fetch threw out of the iteration and both
  doors read it the only way they could: no terminal frame, therefore an orphan,
  therefore Q7 swept the server and DELETEd a job that had FINISHED, and the
  render or align was re-run from zero. A failed fetch is a TRANSPORT fault on
  work that is already done. It is now retried on the reconnect ladder, and the
  one number that makes that possible is owned by
  `electron/crucible/artifacts-owed.ts`: **re-open the stream one frame BELOW
  the lowest artifact still owed**, so the server replays that announcement and
  the SDK (whose `started` set is per call) fetches the file again. Files
  already written stay — sidecar-then-rename makes a frame seen twice the same
  bytes twice. Three rules in that module and each is a refusal to guess: an
  artifact named ONLY by the `done` list forces a full replay (the SDK's
  done-list fallback runs only when nothing was resumed from); **the DIRECTORY
  is asked before the tally** (a download that settled as the socket died is on
  disk and was never announced — believing only what we were told re-fetched two
  of three chunks on every blip); and the ladder's predicate is no longer "did
  we see the terminal frame" but `nothingLeftToRead` — the frame AND everything
  it announced. A ladder that runs out with the job `done` **parks transient**
  (`crucible_artifacts_incomplete`), cancels nothing, and KEEPS the ledger row
  with its `lastEventId` so a later attempt attaches and fetches rather than
  asking for the hour of GPU again.

- **A render cancelled by somebody else is a wait (LOW).**
  `CrucibleRenderNotDone` carries neither `busyLine` nor `transient`, so a
  `cancelled` frame this app never asked for — an operator's `crucible api …
  job cancel`, another client taking the card, a server settling its own lane —
  reddened the row and waited for a person to press Retry.
  `crucible_cancelled_elsewhere`, transient, with a line saying whose cancel it
  was. **Our own Stop keeps its path exactly**: the door's `cancelled` flag is
  set, this arm does not fire, and the queue still tells a stop from a failure
  by its own `stopRequested`.

- **The fake grew one thing a real Crucible has: a finished job's events stay
  readable.** `tools/fake-crucible.js` forgot a job the moment its stream ended,
  so ANY reconnect above a terminal frame answered `404 unknown_job` — which is
  what made a retried artifact fetch look like a restarted server. Finished jobs
  now keep the frames they actually sent and replay them above `Last-Event-ID`;
  a `restart()` still forgets everything, which is the difference the
  `unknown_job` scenarios depend on.

- **Nothing reads `unclaimedSince` for a stranded card, and that is the ruling
  (§F.8, PK14a).** No client-side unloader was built. S14 was rewritten to what
  is actually true now: the load FINISHES (a `holdUntilCancelled` job waiting on
  a DELETE that is refused `409 job_not_cancellable` is a deadlock, not the
  14:29 failure), this side settles its own ledger row, `strandedSince` reads
  the card's own stamp by name, and a sweep with no ledger row for that server
  does not so much as poll it — "nothing in this app comes back for it" is the
  design, asserted, not an omission. The `unclaimedSince` LOG LINE fires only
  where the sweep walks a card and leaves it alone, which `test-crucible-quit-sweep`
  already pins; it cannot fire in S14, because a cancelled load leaves no row.

### PK11 · Reconnect before you cancel (S13) — 2026-09-20

The 14:27 failure was three defects firing in sequence on ONE network blip, with
the book 1,901 of 2,267 chunks through its align.

- **The align door's generic catch now CLASSIFIES.** The error was the SDK's own
  `CrucibleUnreachable`, thrown by a plain SDK call rather than built by a door,
  so it fell past the `CrucibleJobRefused` arm (which forwards Contract 1's pair)
  and `coverage-align-job.ts:859` returned a plain fail: red row, assembly

  membership test — `crucibleUnavailableCause` in
  `electron/crucible/transport-failure.ts`: `CrucibleUnreachable`, a
  `CrucibleServerError`, or anything `transportFailureCause` recognises — and
  composes the line through the one composer (`job.ts crucibleTransientLine`), so

  `UND_ERR_HEADERS_TIMEOUT` and `UND_ERR_BODY_TIMEOUT` joined the errno set —
  undici's three clocks were the one class of wire failure it did not name.

- **A BROKEN STREAM IS NOT A BROKEN JOB.** Q7's one-server sweep (right for a
  server that has gone) cancelled a job that was fine, because the door read "no
  terminal frame" as "the job is lost" — while the resume that would have saved

  pure and exported so the policy can be read without running a render). Every
  attempt is logged by name. The ladder sits INSIDE `withStreamStallClock`'s
  `consume`, so C2's clock keeps running across it, and its budget is
  deliberately under the ten-minute stall window so the two clocks cannot argue.
  A user's Stop (or the stall clock's own DELETE) aborts the ladder at once.
  - A reconnect that finds the job **done** reads the terminal frame and

### PK6 · Foundry becomes a runner under BookForge's queue — 2026-09-20

Owen's ruling 1 (§F), built to the design in §H. Two repos: Foundry
`feat/hosted-runner` (9e0b27d, re-vendored into `foundry-app/`) and BookForge
`pk6/foundry-runner`.

**The rule, as it now stands in code.** BookForge's queue is the lifecycle.
Foundry, when hosted, is a runner: given a DESCRIPTION of one act and a VENUE, it
plans, places, spawns and returns a typed OUTCOME. It stores nothing across calls
and decides nothing about when.

- **F1 + F5 LANDED — the press names a ROW, never a file.** `workspace.ts` split
  every plan in two: `identify*` (press) composes identity — the records file,
  the step, the stamp — and `materialize*` (spawn) makes the book, resolves the
  seed and reads the generation. The request carries `at: string | null` (or
  `deferred.from`) and no path under `derived/`. The lifetimes were backwards: a
  derived book is unlinked by `sweepDerivedBook` at EVERY ending and by
  `sweepStaleDerived` after a day, while a request outlives its row's first
  attempt — Retry re-sends it byte for byte, a resumable Stop leaves it on the
  step, and hosted it is persisted in this app's `queue-engine.json` across
  restarts. `--book … (ENOENT)` was the reliable consequence. `at` is resolved AT
  THE PRESS (`positionOf` when the person was simply standing there), so the
  family's standing rule is untouched: a pointer moved while the job waited still
  cannot change which book is made.
- **`materializeDeferred` is GONE.** A deferral is just an `at` that did not
  exist at the press, so ONE function — `materializeAtSpawn` — materialises every
  row, inside `carry`, after the placement and beside the seed copy and the
  analysis checklist. That position is the rule those two already state about
  themselves: a row that turns out to be waiting for a busy card must leave the
  project exactly as it found it. Its refusal ("the step this was to be made from
  never landed") is unchanged and now covers every row rather than promised ones.
- **F8 LANDED.** `seedRecordsPath` logs by name when the ledger names a seed and
  the disk no longer holds it (a Start over, a deleted step, a moved library).
  The copy's `existsSync` made that a silent no-op and the run paid full price —
  verbatim the defect the seed exists to prevent.
- **Q4 / Contract 2 LANDED, typed.** `RunOutcome` is
  `done | failed{error, stderrTail} | wait{busyLine, standing} | cancelled`.
  `foundry-job.ts` maps `wait` → `stepFailure(busyLine, busyLine)` (PK1's engine
  re-queues on it), `failed` → `stepFailure(error)` with the stderr written to
  `foundry.log` at ERROR, `cancelled` → the stop it always was. A `standing`
  wait parks too, which is what let the `hostedCrucibleServerNotOffered`
  pre-check be DELETED: it existed because a name that window could not match was
  a wait, and a detached `runJob` had no pump slot to give up, so `placeRun`'s
  `for (;;)` retried for ever. That spin is gone — a detached run's wait comes
  back the moment the placement says it — so the check is no longer the
  difference between a park and a hang, only a second registry with a second
  opinion.
- **F3a LANDED.** `Placement.concurrency` (4 on a Crucible chat door, ruling 4)
